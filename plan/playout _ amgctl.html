playout

Description​

amgctl is a powerful command-line interface (CLI) tool designed to manage, deploy, and control various application components. One of its key features is the ability to deploy playout topologies, which represent a set of components responsible for media playout workflows.

Playout Topologies​

The playout command supports a variety of topologies, categorized into Standard and Prefilled topologies. Topologies are predefined combintation of applications that help you quickly deploy a system based on your specific needs.

1. Standard Topologies​

Standard topologies offer more flexibility and allow users to configure the applications based on their specific needs.

a. GENERAL_PLAYOUT

b. GENERAL_PLAYOUT_2

c. PLAYOUT_V2_NDI

d. PLAYOUT_V2_NDIXS

e. PLAYOUT_WITH_REDUNDENCY_V2_NDI

f. PLAYOUT_WITH_REDUNDENCY_V2_NDIXS

g. CEF_TARANG

h. PLAYOUT_WITH_NDI_SWITCHER

i. PLAYOUT_WITH_VANXIO_SIMULCAST

j. PLAYOUT_WITH_TRANSCODER_SIMULCAST

2. Prefilled Topologies​

Prefilled topologies are predefined configurations designed for specific use cases. These topologies simplify deployment by automatically configuring necessary components.

a. Prefilled 1 Topologies​

  1. PREFILL1_NDI-REDUNDANCY-PLAYOUT

  2. PREFILL1_TS-REDUNDANCY-PLAYOUT

  3. PREFILL1_NDI-PLAYOUT

  4. PREFILL1_DELAYED-PLAYOUT

  5. PREFILL1_MINIMAL-LATENCY-PLAYOUT

  6. PREFILL1_BREAKIN-TRANSCODER

  7. PREFILL1_BREAKIN-DEMUXER

Prerequisites​

Before you can use the amgctl CLI to manage and deploy playout topologies, ensure that the following prerequisites are met

  1. Workspace
  2. Addon
  3. Appinfra
  4. Appsecrets
  5. Feed must be created before deploying the playout for that feed.
  6. PLSH must be deployed

FAQs

  1. How to Find the Configuration Documentation

    You can access the configuration documentation here. If you need guidance on configuring the topology.yaml files or are encountering issues, follow this guide to identify the relevant configuration keys:

    1. Player Applications:
      Configurations start with player.****.
      Example: player.deployment_config.uuid

    2. Transcoder, Encoder, Decoder Applications:
      Configurations start with transcoder.****.
      Example: transcoder.deployment_config.uuid

    3. Muxer, Mrr Muxer, and Delivery Muxer Applications:
      Configurations start with muxer.****.
      Example: muxer.deployment_config.uuid

    4. Demuxer, Breakin Demuxer Applications:
      Configurations start with demuxer.****.
      Example: demuxer.deployment_config.uuid

    5. Doordarshan Applications:
      Configurations start with doordarshan.****.
      Example: doordarshan.ops_config.business_config.DDMonitoringTemplate

    6. Delay Server Applications:
      Configurations start with delay_server.****.
      Example: delay_server.deployment_config.uuid

    7. Switcher Applications:
      Configurations start with switcher.****.
      Example: switcher.deployment_config.podType

  2. How to get the deployment name of playout deployment?

    When you run amgctl playout create/update/destroy command, you will get a following response. In this JSON response, there is field called name which you can refer.

        {
            "status": "submitted",
            "task_id": "arn:aws:ecs:us-east-1:xxxxxxxxxxxx:task/xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx",
            "name": "xxxxxxxx"
        }

    Usually, playout deploymnet follow following conventions Playout follows <customer-name>-<channel-id>-<headend-id> for the deployment names. There's a exception on breakin topology depoyments, where it uses <breakin-name>. You can use this name to get the logs of the deployment container.

  3. Pods Stuck in Pending State after changing the AZ of a Nodegroup

    1. Pods belonging to kubernetes statefulset (eg. player) having volume claim templates are disrupted in case existing nodegroups availability zone is changed post deployment.
    2. Following error message can be "status": "submitted", "task_id": "arn:aws:ecs:us-east-1:xxxxxxxxxxxx:task/xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx", "name": "xxxxxxxx"seen in the pods events “volume affinity conflicts” which will cause the pods to be stuck in pending state.
    3. In such scenarios it is recommended to delete the persistent volume claim (pvc) & the persistent volume (pv) for the pending pod from kubernetes in order to allow the associated sts to provision new volumes in the new availability zone.

  4. How to find the palyout PR number?

    When you run amgctl cp app playout create/update/destroy command with --dry-run flag. It creats a pull request in your github repository with same name as the deployment name. You can find out the PR number in the logs of the deployment container

  5. How to connect multi region deployments?

    NDI Redundancy, TS Redundancy topology allows you to connect deployments to cater the multi region use cases. If you want to connect multi region deployment. You can configure the switcher components of these topologies.

      switcher:
        deployment_config:
        prefills:
            mrr:
                automationPrefix: <automation-prefix>
                channelId: <channel-id>
                headendId: <headend-id>

  6. How to connect rehearshal deployment with primary deployment?

    NDI Redundancy topology allows you to connect rehearshal deployments to cater the rehearshal use cases. If you want to connect rehearshal deployment. You can configure the switcher components of this topology.

      switcher:
        deployment_config:
        prefills:
            rehearshal:
            channelId: <channel-id>
            headendId: <headend-id>

    You can keep this empty if you don't want to connect a rehearshal deployment with your primary pipeline

  7. How to connect breakin deployment with primary deployment?

    NDI Redundancy, TS Redundancy topology allows you to connect Breakin deployments to cater the breakin use cases. If you want to connect breakin deployment with your primary pipeline. You can configure the switcher components of this topology.

      switcher:
        deployment_config:
        prefills:
            breakin:
                name: <breakin-name>

    You can keep this empty if you don't want to connect a breakin deployment with your primary pipeline

  8. How to find the Breakin uuid? Breakin uuid is constructed based on following conventions

    1. Breakin Transcoder: <breakin-name>-<transcoder>
    2. Breakin Demuxer: <breakin-name>-<demuxer>

  9. How to enable program recording in ndi_redundancy/ndi topology ?

    Set the following config in the encoder section to true. Setting it to true will orchestrate a peer srt output from encoder, which can be consumed by the VOD workflows.

        encoder:
            deployment_configs:
                prefills:
                    enableProgramRecording: true

  10. How long can the deployment container monitor for argocd sync status for applications ?

    The deployment container can run for atmost 45 minutes. There will be 30 retries, each with a delay of 90s. This is because, when applications are newly deployed it can occasionally take upto 30 minutes to be created in argocd.

    params.dd.ops_config.business_config.NDILiveAudioLangs: incomplete value string | "eng" | "eng,eng"
    11:58PM ERROR failed to export coreservice error="terminating because of errors"
    11:58PM ERROR failed to export config id=topology
    11:58PM ERROR failed to export configs

    • Add NDILiveAudioLangs under the section as given below

        params:
          dd:
           ops_config:
             business_config:
               NDILiveAudioLangs:

    • Set the key's value to a comma-separated list of "eng" entries, with the count matching the number of audio tracks in the input stream

      Example

      Single audio track:

       NDILiveAudioLangs: "eng"

      Two audio tracks:

       NDILiveAudioLangs: "eng,eng"

      Three audio tracks:

       NDILiveAudioLangs: "eng,eng,eng"

player.deployment_config.uuid

What is it?

This field defines the unique identifier (UUID) for the POD in the

deployment. It uniquely identifies the specific instance of the POD.

How is it used?

The uuid is used for referencing and identifying a particular POD

in a cluster or network. It follows a specific naming convention

to help ensure uniqueness across environments.

Naming convention

The recommended format for the uuid is:

<Environment Type>-<customerID>-<FeedID>-<HeadendID>-<POD Type>

Where:

  • Environment Type: Specifies the environment (e.g., production, test, devQA).
  • customerID: A unique identifier for the customer.
  • FeedID: The ID of the feed.
  • HeadendID: The ID of the headend.
  • POD Type: Can be player, switcher, or Doordarshan.

Only lowercase alphabets and hyphens (-) are allowed in the value.

How to get the value?

The value should be a string that adheres to the naming convention

mentioned above, ensuring uniqueness in your deployment.

Example

uuid: "amagi-001-001-player"

This field configures the public output stream protocol URL for

delivering the stream to external clients or services.

How is it used?

The public output protocol determines how the output stream is

accessed and is essential for integrating with external systems

and clients.

You can also specify which interface to output out of using

sdc_iface query params. Supported values: eth0 | eth1 | lo

NOTE:

  • sdc_iface=lo is allowed only for loopback destinations (127.0.0.1)
  • If no interface is provided, default interface is eth0 in k8s and lo in non k8s setups

How to get the value?

Provide a valid stream protocol URL, such as

"rtp://10.10.10.10/?sdc_iface=eth0,rtp://10.10.10.11/?sdc_iface=eth1,rtp://127.0.0.1:9090?sdc_iface=lo"

Supported Values (Examples):

To configure 'srt' in server mode, the following format should be used:

  • srts://0.0.0.0:9090?latency=2000

To configure 'srt' in client mode, the following format should be used:

  • srtc://0.0.0.0:9090?latency=2000

For the remaining protocols, the following formats can be used:

  • udp://0.0.0.0:9090
  • rtp://0.0.0.0:9090?sdc_iface=[eth0|eth1] (sdc_iface is optional)
  • rtp://127.0.0.1:9090?sdc_iface=lo (loopback only)
  • rist://0.0.0.0:9090?mode=listener&latency=2000
  • rist://0.0.0.0:9090?mode=caller&latency=2000

Example

publicOutputProtocol: ""

player.deployment_config.peerInputProtocol

What is it?

It defines the protocol used for peer-to-peer communication between services

in the deployment. It defines the protocol for stream transfer and how one service

connects to and communicates with another service within the same topology.

How is it used?

The peer input protocol is used to establish communication channels between services

such as player-to-transcoder, transcoder-to-switcher, switcher-to-doordarshan, etc.

Different protocols support different transport mechanisms and quality-of-service parameters.

Supported Protocols:

  • ndi:// - Network Device Interface for low-latency video transport

To configure 'srt' in client mode, the following format should be used:

  • srtc://:?latency=<ms> - Secure Real-time Transport with configurable latency

To configure 'srt' in server mode, the following format should be used:

  • srts://:?latency=<ms> - Secure Real-time Transport with configurable latency
  • ndixs://:?protocol=tcp - JPEG XS encoded stream over NDI (NDI Extended)
  • rist://:?mode=<mode>&latency=<ms>&sdc_mode=<mode> - Reliable Internet Stream Transport

How to get the value?

The appropriate protocol depends on the services being connected and the network

requirements. Most topologies have default values, but custom configurations may

require specific protocol settings based on latency, reliability, and network conditions.

The peer input protocol should be the protocol that is used to receive the stream from the upstream peerOutputProtocol.

For clean feed cases use the below format:

peerInputProtocol: "ndi://?sdc_clean_recording=true"

Example

peerInputProtocol: "ndi://"

peerInputProtocol: "srtc://:?latency=100"

peerInputProtocol: "rist://:?mode=client&latency=300&sdc_mode=pod_ip"
